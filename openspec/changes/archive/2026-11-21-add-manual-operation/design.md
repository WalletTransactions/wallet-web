# Design

## Context

Веб уже пишет операции: `aiPush()` (ИИ-карточка траты) и пакетная запись импорта выписки
шлют `POST /sync/push` с `operation[]`. Справочник кошельков и статей грузит
`aiLoadAccounts()` из `GET /api/reports/accounts`, «кошелёк по умолчанию» хранит
`setAiLastWallet`, uuid делает `uuidV4()`. Модальные окна в вебе — нативный `<dialog>`
(форма валюты, `#cur-currency-dialog`). Мотивация и объём — см. proposal.md.

Ограничения: SPA без фреймворка и сборки (одним файлом, ES5), автотестов нет, каждый экран
работает на телефоне (раскладка до ~700px).

## Goals / Non-Goals

**Goals:**
- Одна общая функция записи операции, которой пользуются ИИ-карточка и новая форма.
- Форма на `<dialog>` по образцу формы валюты, без новых зависимостей.

**Non-Goals:**
- Переводы, комиссии, переоценка, правка и удаление (отдельные changes).
- Рефакторинг `app.js` на модули и смена фреймворка (Nuxt и др.) — отдельное решение.
- Определение роли пользователя в леджере на клиенте.

## Decisions

**D1. Общий помощник `pushOperation(op, batchId, opts)`.**
Берёт на себя `POST /sync/push`, один повтор после `403 device_required` через
`/auth/refresh`, `401` → экран входа и разбор кодов ошибок в `{ok, code, status}`. `aiPush`
переводится на него, а тексты ошибок остаются у вызывающих (у ИИ — «трат», у формы —
«операций»). Альтернатива «скопировать aiPush» отвергнута: два места правки одной и той
же логики повтора и идемпотентности.

**D2. Справочник — общий кэш с ИИ-карточкой.**
Форма берёт `aiLoadAccounts()` как есть и дополнительно фильтрует долговые кошельки
(`counterparty_uuid`). Функцию стоит переименовать в нейтральное имя при подходящем случае,
но не обязательно в этом change. Альтернатива «отдельный запрос из формы» дала бы второй
кэш с расхождением данных.

**D3. Фильтр статей по `category_kind` — нужна правка wallet-report.**
В `wallet-api` `account.category_kind` есть (0 — расход, 1 — доход, 2 — оба), но
`AccountRow` в `wallet-report` его не отдаёт. Нужно добавить поле `category_kind`
(integer 0–2, у кошельков 2) в `GET /api/reports/accounts` — отдельный change в репозитории
wallet-report; он обратно совместим (добавляется поле). Пока поля нет, веб показывает все
статьи для обоих типов (спека допускает: «ответ без `category_kind`»). Порядок: сначала
выкатывается wallet-report, потом веб, но веб работает и до этого — просто без фильтра.
Альтернатива «выводить вид по истории операций» отвергнута: ненадёжно для новых статей.

**D4. Роль читателя — через ответ сервера.**
Веб не знает свою роль в леджере на этом экране, поэтому кнопка видна всем, а читатель
получает `403 reader_cannot_write` и понятное сообщение. Альтернатива «запросить роль
заранее» потребовала бы нового вызова или поля в `/auth/me`; ради редкого случая не
оправдано.

**D5. Дата и время — как в ИИ-карточке.**
Поля `<input type="date">` и `<input type="time">`, в проводку — «ГГГГ-ММ-ДД ЧЧ:ММ:СС» без
часового пояса; это бизнес-дата, как требует контракт `OperationPushRow`.

**D6. Число знаков суммы — по `precision` кошелька.**
`AccountRow.precision` — текст («2»), у категории пустой. Проверка идёт на клиенте, сумма
в проводку уходит строкой, чтобы не терять точность.

**D7. Лента после записи и период.**
Как у ИИ-карточки: `reportsCache = {}` и перезагрузка ленты; поиск, фильтры и выбор
сбрасываются по общему правилу перезагрузки ленты. Период по умолчанию — 12 полных
месяцев, заканчивая ПРОШЛЫМ (`defaultPeriodToIso`, требование `reports-shell`), поэтому
расход за сегодня после записи в ленту не попадает. Решено (владелец, 2026-11-21): период
сам не меняется, а над лентой остаётся строка «Записано: … — вне выбранного периода» с
кнопкой «Показать», которая ставит период на календарный месяц операции
(`setPeriodPreference`, как ручной выбор). Альтернативы — автоматически расширять период
(молча меняет сохранённый выбор) и ограничиться сообщением (пользователь не видит операцию).

**D8. e2e-тесты: Playwright в `wallet-web/e2e/`, без изменений в `site/`.**
`app.js` — один IIFE без экспортов, юнит-тесты функций невозможны, поэтому тесты идут
через браузер. Каталог со своим `package.json`, образ `wallet-web`
(`Containerfile` копирует только `site/`) не затрагивается. Зависимость — `playwright-core`
(без загрузки браузера), запуск — встроенный `node --test` (без отдельного раннера),
браузер — системный Chrome (`E2E_CHROME`, по умолчанию `/usr/bin/google-chrome`).
Адрес — `E2E_BASE_URL`, по умолчанию `http://127.0.0.1:8091` (test-контур на этом же
хосте; он доступен по http только с localhost, остальным нужен https :8444). Объём —
только эта фича (форма «+ Операция»), общий дымовой набор не входит.

**D9. Данные тестов.**
Перед набором тест создаёт пользователя `POST /auth/register` (случайный email вида
`e2e+<время>@…`, пароль случайный, в `/tmp` не пишется) и входит по паролю; пользователь
получает собственный леджер, чужие данные не затрагиваются. Если `GET /auth/methods`
показывает закрытую регистрацию, тесты помечаются пропущенными с понятным сообщением.
Для живых проверок создаются кошелёк и статьи через `POST /sync/push` из самого теста
(`account`, `account_operating`, справочник валют уже есть в леджере). Негативные ответы
(`reader_cannot_write`, `missing_reference`, `5xx`, `device_required`) подменяются
`page.route`: воспроизводить их на живом сервере дороже и хрупче. Файла с паролем в
репозиторий не кладётся; учётка для ручных прогонов — в
`~/.config/wallet-secrets/test/`.

## Risks / Trade-offs

- [e2e на живом test-контуре зависят от его состояния и версий сервисов] → тест создаёт
  собственного пользователя и не читает чужие данные; ручной запуск, не обязательный
  шаг CI.
- [Накопление тестовых пользователей на test] → случайный префикс email `e2e+`, чистка
  по необходимости отдельной командой; это не часть этого change.

- [Без `category_kind` пользователь может записать доход в категорию расхода] → сервер
  это не запрещает (`category_kind` — подсказка клиенту); после выката wallet-report список
  фильтруется, до того — пометка в README.
- [Перенос `aiPush` на общий помощник задевает работающую ИИ-запись] → ручная проверка
  обоих путей (ИИ-карточка и импорт выписки) в браузере после правки.
- [Двойная отправка] → кнопка блокируется на время запроса; повтор идёт с теми же
  `batch_id`/`uuid`, сервер вернёт сохранённый ответ.
- [Дата вне периода — «пропала» операция] → текст успеха называет сумму, статью и кошелёк;
  периода не меняем.

## Migration Plan

Только статика. Выкатка веба — обычной сборкой образа `wallet-web`; откат — предыдущий
образ. Порядок: wallet-report (`category_kind`) → wallet-web; обратного порядка не
требуется.
