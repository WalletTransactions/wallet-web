# wallet-web

Статика проекта (SPA) — то, что раньше рендерил `wallet-bff`
на сервере (HTML-шаблоны в C++), теперь плоские файлы (`site/`), отданные
nginx. **wallet-bff как сервис упразднён** — после перехода на SPA у него не
осталось ни одной причины оставаться отдельным процессом (см. "Куда делся
wallet-bff" ниже).

У сервиса нет собственного HTTP API — [`openapi.yaml`](site/openapi.yaml)
честно фиксирует это (SPA-фолбэк + два по-настоящему статических адреса,
см. ниже). Файл лежит внутри `site/`, а не рядом с README, как у остальных
трёх сервисов, — единственная копия физически там же, откуда её отдаёт
nginx (см. "Документация" ниже).

```
браузер --(GET /)--> wallet-gateway --> wallet-web (nginx, статика)
                          index.html подключает app.js
браузер --(app.js: GET /auth/me, credentials: include)--> wallet-gateway --> google-auth
                          200 {name,email,role} -> "Отчёты" (стартовый экран)
                          401 -> экран логина
браузер --(app.js: кнопка "Кошельки" на "Отчёты")--> дашборд-CRUD (renderDashboard)
браузер --(app.js: POST/DELETE /api/wallets)--> wallet-gateway --> wallet-api
браузер --(app.js: GET /api/reports/balance|income|expense|expense-structure)--> wallet-gateway --> wallet-api
```

## Экран «Отчёты» (`app.js::renderReports`) — стартовый после логина

**Стартовый экран после Google-логина — с 2026-09-06.** Раньше (см. историю
этого README) `boot()` после `GET /auth/me` вёл на `renderDashboard()` —
демо-CRUD кошельков, а «Отчёты» были кнопкой оттуда, на два клика вглубь.
Дизайн (`servers/Design/.../Отчёты - веб.dc.html`) описывает отчёты как то,
что видит пользователь сразу после авторизации, а не как подраздел
демо-формы — теперь так и есть: `boot()` при успешном `GET /auth/me` сам
выставляет `currentUser` и сразу зовёт `renderReports()`. Демо-CRUD кошельков
никуда не делся (это единственная функциональность wallet-api, которую вообще
можно проверить руками) — просто стал соседним экраном, кнопка «Кошельки» на
«Отчётах» ведёт туда, кнопка «Отчёты» там — обратно. `logout-btn`/
`admin-link-btn` теперь есть на ОБОИХ экранах (`adminLinkButtonHtml` —
общая функция) — раньше они были только на дашборде, а без него выйти или
попасть в список пользователей было бы неоткуда.

Поверх `GET /api/reports/balance`/`income`/`expense`/`expense-structure`
(`wallet-api`, org/docs/TODO_mobile_sync.md, Фаза 4). Леджер на MVP
один на пользователя (см. план, п. 1.3), поэтому переключателя леджера в UI
нет — только дата/период и валюта эквивалента (ISO-код, текстовое поле, по
умолчанию `USD`).

Три состояния эквивалента (`formatEqAmount` в `app.js`) — та же разметка, что
и в Android-приложении (см. `android-wallet/docs/ARCHITECTURE.md`, "Три состояния
эквивалента"): число без пометки — счёт уже в валюте эквивалента
(`currency_uuid` строки == `eq_currency_uuid` ответа), `≈ число` — пересчитано
по курсу, `~` без числа — курса не нашлось. В «Итого» те же правила, но `~`
не прячет число, а помечает его как заниженное (`incomplete`).

`.card.wide` (900px вместо обычных 460, `style.css`) — существовавший, но
раньше нигде не применявшийся класс; включён на списке пользователей
(`setWide`, было упущено при переезде админ-таблицы из server-rendered
google-auth в эту SPA). «Отчёты» сами по себе с 2026-09-06 больше НЕ через
`.card` вовсе — см. следующий раздел.

### Дизайн Organic и сайдбар-навигация (2026-09-06)

По прямому запросу — взять дизайн `servers/Design/.../Отчёты - веб.dc.html`
и перенести в реальный код: **всё приложение целиком** (не только «Отчёты»),
**сайдбар как в макете**, шрифты — **системные, без внешних запросов**
(Caprasimo/Figtree в макете — Google Fonts, а проект — LAN-only MVP, см.
`org/docs/TODO_mobile_sync.md`, 1.4). Подробное обоснование каждого решения —
там же, раздел «Дизайн Organic перенесён в реальный код wallet-web»; здесь —
что именно и где искать в коде.

- **`style.css`** — токены дизайн-системы Organic (тёплый фон `#f5ead8`,
  поверхность `#fff8ec`, акцент терракота `#c67139`, пилюльные кнопки/поля,
  тени карточек) вместо прежней нейтральной Google-палитры. Общий файл с
  server-rendered страницами google-auth (см. "Откуда этот файл" ниже) — их
  вид меняется тем же заходом, не отдельной правкой. `--font-display`/
  `--font-body` — системные стеки без Google Fonts, `ui-rounded` (там, где
  браузер его знает) приближает роль Caprasimo для заголовков/крупных сумм.
- **«Отчёты» — полноэкранный сайдбар-кабинет**, не карточка по центру, как
  все остальные экраны (логин/дашборд-CRUD/список пользователей/ошибка —
  они не изменились структурно, только цветом/шрифтом). `body.reports-open`
  (класс на `<body>`, ставит `renderReports()`, снимает `setWide()` — её
  вызывает любой ДРУГОЙ экран верхнего уровня) переопределяет `#app.card`
  через `all: unset` в CSS, дальше раскладку целиком задаёт `.reports-shell`
  (`<aside>` + `<main>`) в `app.js`.
- **Навигация сайдбара** (`REPORTS_NAV` в `app.js`) — 11 пунктов в 4 группах,
  структура из `VIEWS` дизайна: Обзор / Список операций · Куда уходит
  (Структура расходов / Категории во времени / Места и подписки) · Когда
  (Календарь трат / Ритм недели / Темп месяца) · Насколько изменилось
  (Динамика по месяцам / Что изменилось / Средний чек и частота). Реальные
  данные — под «Обзор», «Список операций» (с 2026-09-06), «Структура
  расходов», «Динамика по месяцам» и «Категории во времени» (переключение
  между ними — `switchReportsView()`, БЕЗ повторного запроса — все пять
  загружены целиком при открытии «Отчётов»; «Динамика» дополнительно лениво
  подгружает разбор выбранного месяца по клику, «Категории во времени» —
  переключение между уже загруженными карточками); остальные шесть
  задизейблены (`.nav-item:disabled`, бейдж «скоро») — не убраны совсем,
  чтобы был виден масштаб задуманного отчёта. Подробности "Динамики",
  "Списка операций" и "Категорий во времени" — свои разделы ниже.
  **Отдельный, полноэкранный «Что изменилось» (год-к-году, не то же самое,
  что панель «Что изменилось сильнее всего» на «Обзоре») по-прежнему
  отмечен в плане (`TODO_mobile_sync.md`) как необходимый к переносу** —
  прямое указание пользователя, не реализовано.
- **Аватарка+имя в углу сайдбара** (`avatarHtml`/`wireAvatarFallback`,
  2026-09-06, по прямому запросу) — `GET /auth/me` теперь отдаёт `picture`
  (URL Google-аватарки — НЕ через JWT, отдельным походом в БД именно внутри
  этого обработчика, см. README google-auth, "Аватарка"). Настоящий `<img>`,
  не `background-image`, как у иконок категорий — источник чужой хост
  (Google), не наш blob-стор, `onerror` меняет его на кружок с первой
  буквой имени (пусто/битый URL/нет сети до Google не оставляют дыру в
  интерфейсе).
- **Сворачиваемое меню** (`setSidebarCollapsed`, 2026-09-06, по прямому
  запросу) — кнопка «☰» в `reports-header` (не в самом сайдбаре: иначе
  пропадала бы вместе с ним при `width: 0`). Состояние — в `localStorage`,
  переживает перезагрузку; применяется сразу в разметке при построении
  экрана (не toggle'ится после вставки), чтобы не было видно анимации
  "развернулось и тут же свернулось обратно" при каждом заходе. Карта
  расходов пересчитывается по `transitionend`, не сразу по клику —
  `clientWidth` сайдбара меняется только когда CSS-transition реально
  закончится.

### «Обзор» (`refreshPeriod`/`renderOverview*`) — по дизайну, без групп и обязательных платежей

По прямому запросу — "сделай обзор по дизайну. группы по прежнему не нужны.
обязательные платежи не нужны" (уточнено: помесячную SQL-агрегацию строить
сразу, не откладывать в план). Заменил прежние отдельные таблицы "Баланс на
начало дня"/"Доход"/"Расход" (были здесь с самого первого захода Фазы 4)
целиком — четырьмя панелями:

- **4 KPI-плитки** (`renderOverviewKpis`) — Расход/Доход/Итог (доход минус
  расход)/Остаток (на конец периода, `f_balance_to_date` на день ПОСЛЕ
  `period-to` — она считает строго до даты). Чип сравнения (`kpiChipHtml`,
  % к cmp-периоду, цвет по тому, хороший ли рост для ЭТОЙ метрики — рост
  расхода плохой, рост дохода хороший) — только когда выбран режим
  сравнения; у "Остатка" чипа нет вовсе (точку во времени не с чем
  сравнивать в процентах).
- **"Расход по месяцам · 12 месяцев"** (`renderOverviewMonthlyChart`,
  `GET /api/reports/income-expense-by-month`) — фиксированное окно
  "последние 12 месяцев, заканчивая месяцем period-to", НЕЗАВИСИМО от
  period-from (та же логика, что в дизайне — "12 месяцев" отдельная
  витрина, не сам выбранный период). Обычные `div`-столбики (расход +
  доход тоньше рядом), без библиотек — тот же приём, что и весь остальной
  этот экран.
- **"Что изменилось сильнее всего"** (`renderOverviewBiggestMoves`,
  `GET /api/reports/expense-biggest-moves`) — диврегирующая полоса на
  категорию (слева — стали тратить МЕНЬШЕ, справа — БОЛЬШЕ, те же цвета,
  что в дизайне). Видна только при выбранном периоде сравнения — без него
  плейсхолдер с подсказкой выбрать режим сравнения выше, запрос вообще не
  шлётся (серверу нечего было бы ответить — `cmp_from`/`cmp_to` там
  обязательны).
- **Мини-"Структура"** (`renderOverviewMiniStructure`) — топ-5 категорий,
  переиспользует УЖЕ загруженные данные вкладки "Структура"
  (`lastStructureData`, см. ниже) — отдельного запроса нет, обе вкладки
  грузятся одновременно при открытии "Отчётов". Кнопка "Подробно →"
  переключает на саму вкладку "Структура" (`switchReportsView('struct')`).
- **"По дням недели"** (`renderOverviewWeekdayChart`,
  `GET /api/reports/expense-by-weekday`) — 7 столбиков, Пн..Вс, расход (не
  доход — "ритм" в дизайне про то, в какие дни тратят).

Ни группы категорий, ни "обязательные платежи" из дизайна сюда не входят —
по прямому указанию пользователя (см. коммит-сообщение выше); подробности
и обоснование каждой SQL-функции — `org/docs/TODO_mobile_sync.md`, раздел
"Экран «Обзор» по дизайну — без групп и без обязательных платежей".

**Проверено интеграционными тестами** (`test_reports.cpp`, 3 новых): zero-fill
месяцев/дней недели без операций (месяц/день без единой операции — это
честный "0.00" на графике, а не пропавший столбец и не "неполные данные"),
сортировка "что изменилось" по модулю дельты с учётом `limit`. **Проверено
jsdom-харнессом**: значения плиток, число столбцов графиков (12/7), появление
и пересчёт чипов/панели "что изменилось" при переключении режима сравнения,
переход "Подробно →" — без ошибок.

### «Список операций» (`refreshOperations`/`renderOps*`/`opsMatchesFilter`)

По прямому запросу — "реализуй страницу Список операций из дизайна" (`ops` в
`VIEWS`/`servers/Design/.../Отчёты - веб (офлайн).html`). Единственный новый
эндпоинт — `GET /api/reports/operations` (обёртка над
`f_operations_for_period`, `000007_operations`) — в отличие от ВСЕХ
остальных отчётов отдаёт ВСЕ операции периода целиком, БЕЗ поиска, фильтра
по типу/категории/кошельку и без пагинации на сервере: ответ грузится один
раз за период (вместе с «Обзором»/«Структурой»/«Динамикой», см. конец
`refreshPeriod()`), а поиск/фильтры/группировка по дню/«Показать ещё»
(`opsState`, лимит 60, растёт на 60 за клик) — целиком на клиенте, тем же
приёмом, что и сам design-прототип экрана держит всю ленту в памяти и
фильтрует без похода в сеть.

- **`kind`** каждой строки — `expense`/`income`/`transfer`, тот же признак
  `acc_from_is_operating`/`acc_to_is_operating`, что и везде в отчётах.
  Разновалютный перевод между кошельками хранится ДВУМЯ проводками через
  системную категорию Transfer (`operation_link`) и приезжает сюда как
  обычные `expense`+`income` по этой категории — то же самое, что уже
  делают `f_expanse_by_category_for_period` и остальной отчёт (см. память
  проекта: переводы считаются расходом в отчётах). `kind: "transfer"` —
  только у прямой одновалютной проводки кошелёк → кошелёк; `category_uuid`/
  `category_name`/`icon_sha256`/`wallet_uuid`/`wallet_name` у неё пустые
  (SQL `NULL`, см. `db.hpp`) — участвуют ОБА кошелька (`from_uuid`/`to_uuid`,
  заполнены для любого `kind`), а не один кошелёк и категория.
- **Тулбар** (`renderOpsFilters`) — поиск (по комментарию/категории/обоим
  счетам, `input`-обработчик меняет только `opsState.q` и зовёт
  `renderOpsBody()`, САМ `#ops-search` не перерисовывается — иначе на
  каждое нажатие клавиши терялся бы фокус курсора), сегментный переключатель
  типа, чипы категорий/кошельков. Списки чипов — из ВСЕГО периода
  (`opsDistinctCategories`/`opsDistinctWallets`), не из уже отфильтрованных
  строк: иначе выбор, скажем, типа "Доход" на лету убирал бы чипы категорий
  расхода, и не было бы куда вернуться к "Все статьи".
- **Список, сгруппированный по дню** (`opsGroupByDay`) — строки уже
  отсортированы сервером (`ORDER BY date DESC`), группировка идёт по
  порядку, без повторной сортировки; «Сегодня»/«Вчера» — по РЕАЛЬНОЙ текущей
  дате (не захардкожены, как в дизайне). Клик по строке выбирает операцию
  (`opsState.sel`, повторный клик снимает выбор).
- **Сайдбар** — «Итого по фильтру» (Расход/Доход/Итог/Средний расход,
  посчитаны на клиенте из уже загруженных `amount_eq`, с `~`-префиксом при
  `incomplete`), «Статьи в выборке» (топ-5 категорий расхода в ТЕКУЩЕЙ
  выборке, та же полоса доли `.reports-bar`, что и на «Структуре»; клик —
  фильтр по этой категории) и разбор выбранной операции (появляется, только
  если что-то выбрано; своя сумма+валюта, направление, комментарий).

Один делегированный `click`-обработчик на весь `#view-ops`
(`wireOpsEvents`) — чипы/кнопки/строки перестраиваются на каждый
`renderOpsBody()`, навешивать заново слушатели на каждый элемент после
каждой перерисовки было бы и дороже, и хрупче.

**Проверено:** SQL-функция — вручную против живого Postgres (`podman compose
up -d db` + `migrate.sh wallet up`): классификация `kind`, заполнение
category/wallet по стороне проводки и их `NULL` у `transfer`, округление
`amount` по precision своей валюты — да, `amount_eq` уже округлён внутри
`v_operation_eq`; плюс интеграционный тест `test_reports.cpp`
(`operations_for_period_classifies_kind_and_fills_category_or_wallet_by_side`).
Сама вкладка (`app.js`) — НЕ прогнана через jsdom-харнесс (в отличие от
"Структуры"/"Динамики" выше) и не открыта в настоящем браузере — сборка/
редеплой C++-сервиса не выполнялись в этом заходе.

### «Динамика по месяцам» (`refreshDynamics`/`renderDynamics*`) — переход из «Обзора»

По прямому запросу — "отчет динамику по месецам. и переход на него. из
обзора. по дизайну". Пункт сайдбара `dyn` (был задизейблен) включён; на
«Обзоре» появилась кнопка «Вся динамика →» рядом с «Расход по месяцам».
НИ ОДНОЙ новой SQL-функции — целиком переиспользование уже существующего:
сам график — `f_income_expense_by_month` (та же функция, что мини-график
«Обзора», окно шире — 24 месяца вместо 12, независимо от `period-from`),
разбор выбранного месяца по категориям — `expense_structure_for_period`
(та же функция, что вкладка «Структура», `cmp` — предыдущий календарный
месяц).

Урезано относительно дизайна (`isDyn` в макете), с обоснованием в
`org/docs/TODO_mobile_sync.md` (раздел «„Динамика по месяцам“ + переход из
„Обзора“»): один режим — месяц (без переключателя день/неделя/месяц,
агрегации по дням/неделям нет ни у одной отчётной функции), без линии
«среднее за 3» (SVG-полилиния на flex-барах с процентной высотой развела бы
координаты линии и реальных вершин столбцов).

Клик по столбцу (24 месяца) выбирает месяц — 4 статистики
(Расход/Доход/Итог/% к пред. месяцу, тот же `kpiChipHtml`, что на «Обзоре»)
+ топ-6 категорий (сдвиг доли в п.п., тот же `pp_delta`, что на
«Структуре» — не денежная дельта, как в дизайне). Автовыбор — последний
месяц окна. «Год к году» — сумма расхода по календарным годам ИЗ ТЕХ ЖЕ 24
месяцев, без отдельного похода в базу.

### Кэш ответов `/api/reports/*` — «Назад» без похода в сеть (2026-09-07)

По прямому запросу — "можем по нажатию назад восстанавливать ранее
полученные значения, перезапрос только по кнопке обновить (и если нужные
данные не были запрошены)". Раньше `goReportsBack()` восстанавливал фильтр
и звал `refreshPeriod()`, который перезапрашивал ВСЕ вкладки заново по сети
— даже если под точно такие же значения фильтра только что грузили те же
самые данные (типичный случай: зашли в «Динамику» с «Обзора», посмотрели,
нажали «Назад» — «Обзор» перезагружался целиком, хотя ни период, ни валюта
за это время не менялись).

`fetchReport()` — единственное место, откуда уходит любой запрос к
`/api/reports/*` — теперь обёрнуто кэшем: ключ — путь и query-строка
целиком (`path + '?' + query`), значит две ЛОГИЧЕСКИ одинаковые выборки (тот
же период, та же валюта, тот же режим сравнения — то есть в точности то
состояние, которое `captureReportsState()` запомнил в `reportsHistory` ДО
перехода) неотличимы и переиспользуют один и тот же ответ. Кэшируется
только УСПЕШНЫЙ ответ (`res.ok`, не 401 — тот вообще не данные, а сигнал
"перелогинься", и не HTTP-ошибка — ей не место "залипать" в кэше до
следующего настоящего «Обновить»).

Ключевое следствие: **никакого отдельного кода под «Назад» не понадобилось**
— `goReportsBack()` не изменился ни строкой. Он просто ставит старые
значения фильтра в поля и зовёт тот же `refreshPeriod()`, что и раньше;
раз при переходе "с деталями" данные под старые значения УЖЕ грузили (см.
"Кнопка «Назад»" выше — `renderReports()` грузит все вкладки разом, ещё до
первого перехода), `fetchReport()` отдаёт кэш вместо сети сам, прозрачно
для вызывающего кода. Второй пункт запроса — "перезапрос... если нужные
данные не были запрошены" — тоже бесплатно: любая НОВАЯ комбинация
параметров (другой период, другая категория и т.п.) даёт другой ключ кэша и
уходит в сеть как обычно.

«Обновить» (`#period-refresh-btn`) — ЕДИНСТВЕННОЕ место, где кэш нарочно
сбрасывается целиком (`reportsCache = {}`) перед вызовом `refreshPeriod()`:
единственное явное намерение пользователя "не верь старым данным, спроси
сервер заново". Смена самого фильтра (`period-from`/`to`, `eq-currency`,
`structure-cmp-mode`) кэш НЕ трогает — не нужно, другие значения полей сами
дают другой ключ, первый запрос под них в любом случае уйдёт в сеть; заодно
побочный эффект — смена `structure-cmp-mode` больше не тянет по сети
вкладки, которые от режима сравнения не зависят (график по месяцам,
"Список операций", "Категории"), а раньше `refreshPeriod()` перезапрашивал
их вместе со всеми.

Кэш живёт в модульной переменной (`reportsCache`) РОВНО столько же, сколько
и `reportsHistory` — `renderReports()` сбрасывает оба разом при каждом новом
заходе на "Отчёты": пока пользователь был на "Кошельках", он мог добавить
операцию/кошелёк, и старые числа того же периода больше не актуальны —
кэш ПРЕДЫДУЩЕГО захода тут не годится, а не только история переходов. Внутри
ОДНОГО открытого "Отчётов" — между вкладками, «Назад», сменой режима
сравнения — кэш живёт и работает, как описано выше.

**НЕ проверено** — ни jsdom-харнессом, ни в настоящем браузере: сборка/

### Баг: 28..31-е число ломало окно "12/24 месяца" (`refreshPeriod`/`refreshDynamics`/`refreshCategories`, 2026-09-07)

```js
var fromDate = new Date(toStr + 'T00:00:00');
fromDate.setMonth(fromDate.getMonth() - N);
fromDate.setDate(1);
```

`toStr` (`period-to`) — с тех пор, как её дефолт стал "последний день

на дне 29/30/31, если ЦЕЛЕВОЙ месяц короче этого дня (30 сентября нет,
28/29 февраля и т.д.), молча "перепрыгивает" в СЛЕДУЮЩИЙ месяц (31 августа
минус 11 месяцев — це­ле­вой сентябрь, там только 30 дней, день 31
переполняется в 1 октября) — а `setDate(1)`, который идёт СЛЕДОМ, только
фиксирует уже искажённый (более поздний на месяц) результат, не исправляет
его. Итог — окно короче на месяц и начинается на месяц ПОЗЖЕ задуманного;
буквально это и увидел пользователь: должен был быть июнь (условно), стал
июль.

`shiftMonth()`/`lastDayOfMonth()` (использует "Динамика") этому не
подвержены — их входной аргумент уже "YYYY-MM-01" (день 1 гарантирован ДО
`setMonth`), поэтому переполнения не бывает никогда. Тот же порядок
применён и здесь — `setDate(1)` ПЕРЕД `setMonth()`, не после, во всех трёх
местах:

```js
var fromDate = new Date(toStr + 'T00:00:00');
fromDate.setDate(1);
fromDate.setMonth(fromDate.getMonth() - N);
```

Один и тот же день (1) для ЛЮБОГО месяца существует всегда — `setMonth`
после этого не переполняется ни при каком `toStr`.

### «Структура расходов» (`refreshStructure`/`renderStructureResult`/`renderTreemap`)

Собственный пункт сайдбар-навигации (см. "Дизайн Organic и сайдбар-навигация"
выше) — поверх `GET /api/reports/expense-structure`. Реализация экрана
"структура" из дизайна (`servers/Design/.../Отчёты - веб.dc.html`, `isStruct`)
— два столбца: слева «Карта расходов» (treemap), справа «Категории» (список
с полосой доли, `.reports-bar`). Без переключателя "Категории/Группы" — в
реальной схеме БД (`account`) понятия "группа категории" нет вообще,
категории плоские.

**Карта расходов (`renderTreemap`/`squarifyTreemap`)** — добавлена
2026-09-06 по прямому запросу "сделай такой же график, как в дизайне".
Дизайн подгонял 17 прямоугольников руками под придуманные данные; здесь —
настоящий squarified-алгоритм (Bruls/Huizing/van Wijk, 1999, тот же принцип,
что в d3-hierarchy и большинстве библиотек treemap): на каждом шаге
откусывает от оставшегося прямоугольника одну строку плиток вдоль его
короткой стороны, набирая в неё элементы, пока это не ухудшает худшее
соотношение сторон в строке. Работает под любое число категорий и реальную
ширину контейнера (`el.clientWidth`, не квадратные проценты) — перестраивается
заново в момент, когда вкладка «Структура» становится видимой (пока скрыта
`hidden`-атрибутом, `clientWidth` читается как 0, строить по нему нечего),
не только при загрузке данных: `lastStructureData` кэширует последний ответ
ровно для этого. Палитра плиток — 12 цветов `PALS.Терракота` из дизайна;
цвет текста на плитке (светлый/тёмный) выбирается по относительной яркости
фона, а не один on-color на все плитки, как в макете, — палитра вперемешку
тёмная и бледная. Категория без курса (`amount_eq` пустая строка) или без
суммы в текущем периоде (`"0"`, только у "исчезнувшей" при сравнении
периодов) плиткой не рисуется — площадь для неё либо неизвестна, либо
буквально ноль; их количество показано отдельной строкой под картой.

Период сравнения (`computeCmpRange`) — "Предыдущим периодом"/"Тем же периодом
год назад" из дизайна, выбор в `<select id="structure-cmp-mode">`; сервису
достаются уже готовые `cmp_from`/`cmp_to` (see openapi.yaml), сам он про
"предыдущий"/"год назад" не знает ничего. Категория, у которой в текущем
периоде сумма 0, но она была в периоде сравнения (`amount_eq: "0"`,
отрицательный `pp_delta`), всё равно попадает в список справа (не на карту,
см. выше) — иначе "исчезнувшая" статья была бы не видна.

**Проверено jsdom-стендом (не настоящим браузером)** — маленький разовый
харнесс подставлял `window`/`document` через `jsdom` и мок `fetch`, гонял
`app.js` как есть. Для карты — отдельно: 10 категорий (включая без курса и
"исчезнувшую"), проверены геометрия каждой плитки (без `NaN`, без
отрицательных размеров, без выхода за границы контейнера), суммарная
площадь всех плиток ТОЧНО равна `containerW × containerH` (без зазоров и
наложений — математическое свойство правильно реализованного squarify, не
просто "выглядит похоже"), правильное склонение "N категорий" в сноске, и
что одна-единственная категория корректно занимает контейнер целиком.

повторить (оба удаления идемпотентны) — в обратном порядке был бы риск
идентичности без данных, которой они принадлежат, и ничьих данных в
wallet-api. Это два независимых сервиса с разными базами — общей транзакции
на оба шага нет и быть не может.

см. `account_deletion_repo::DeleteStatus::kOwnsSharedLedger`) показывается
как есть через `window.alert` — серверное сообщение уже объясняет, что
сначала нужно передать владение (`POST /api/ledger/transfer-owner`) или
удалить лишних участников (`DELETE /api/ledger/members/{user_id}`), второй
запрос (`/auth/me`) в этом случае не уходит вовсе — идентичность остаётся
нетронутой, пока не разберутся с общим кошельком.

обычный `renderLogin()`: единственный экран, куда пользователь попадает уже
без всякой сессии сразу ПОСЛЕ своего же необратимого действия, поэтому
сообщение — прямо на экране входа (новый необязательный параметр
`renderLogin(message)`), а не отдельный клик "ОК" в момент, когда действие
уже завершено.

**НЕ проверено** — ни в настоящем браузере, ни на живом стеке `wallet-api`+

### Экран «Пользователи» (`renderAdmin`/`renderAdminTable`) — агрегаты и «Посмотреть как клиент»

По прямому запросу — админ должен видеть не только email/роль, но и сколько

**Сшивка двух источников.** `renderAdmin()` сначала запрашивает `GET

`POST /api/reports/admin/users/stats` с id оттуда (wallet-report —

## Почему nginx, а не сам гейтвей

У `wallet-gateway` (cpp-httplib) технически есть `set_mount_point()` — раздать
статику можно было бы прямо там, без нового сервиса вообще. Осознанно выбран
nginx:

- Ближе к тому, что реально стоит в проде перед SPA (nginx/CDN), а не
  самодельный роутер — тот же принцип, что уже применён к самому гейтвею
  (см. его README: "то же самое в проде сделает AWS ALB").
- gzip/кэш-заголовки/условные запросы — из коробки, без строчки кода.
- Явное разделение ответственности: гейтвей — только маршрутизация и
  грубый JWT-гейт, отдача файлов — не его профиль.

Плата за это — отдельный процесс/контейнер и то, что локально без Docker
нужен свой `nginx.exe` (в отличие от остальных C++-сервисов, которые тут
собираются одной и той же связкой cmake — см. "Запуск без Docker" ниже).

## Как SPA понимает, залогинен ли пользователь

Cookie `session` — **httpOnly** (см. README google-auth, `auth::set_session_cookies`)
специально, чтобы её не могла прочитать (и угнать через XSS) никакая
JS-страница — в том числе эта. Поэтому `app.js` не проверяет cookie сам, а
дёргает `GET /auth/me` (новый эндпоинт в google-auth, см. его README) с
`credentials: 'include'` — браузер сам приложит cookie, сервер сам проверит
подпись и вернёт:

- `200 {"id","email","name","role"}` — залогинен, рендерим дашборд;
- `401` — не залогинен (или токен истёк без валидного refresh), рендерим
  экран логина.

Дальше все API-вызовы (`/api/wallets`) идут тем же приёмом — `credentials:
'include'`, без единого явного обращения к самому токену из JS.

## Куда делся wallet-bff

Раньше `wallet-bff` был "backend for frontend" — сервис, единственная
задача которого была рендерить HTML на сервере (читал JWT сам, вставлял
имя/email в шаблон). Как только фронтенд стал SPA (статика + `fetch()`),
эта задача исчезла целиком:

- Рендер страниц — теперь плоские файлы здесь, в `site/`.
- Проверка "залогинен ли" — `GET /auth/me` на google-auth (см. выше) вместо
  `session::current_user()` в wallet-bff.
- `POST /logout` — SPA дёргает `POST /auth/logout` на google-auth
  напрямую (он уже возвращает `204` и чистит cookies сам — обёртка
  wallet-bff была не нужна даже раньше, просто заодно проксировала).

Ни одной причины держать промежуточный процесс не осталось — сервис удалён
целиком (не оставлен "на всякий случай": в этом проекте так же поступили с
CRUD кошельков внутри google-auth, когда он выделился в wallet-api — держать
мёртвый код хуже, чем восстановить его из истории git/чата, если понадобится
снова).

## Откуда этот файл (style.css)

`site/style.css` — объединение CSS, что раньше independently держали
wallet-bff и google-auth (были почти идентичны намеренно, см. старую версию
README wallet-bff — "выглядеть должно как одно приложение"). Теперь один
файл, один источник — на него ссылаются и эта SPA, и оставшиеся
server-rendered страницы google-auth (`index`, `confirm-signup`, ошибка,
список пользователей) через относительный `<link href="/style.css">` —
резолвится в этот сервис только если открыто через гейтвей (см. ниже).

С 2026-09-06 это ещё и единственное место, где живёт дизайн-система Organic
(см. "Дизайн Organic и сайдбар-навигация" выше) — токены в `:root`
(`--bg`/`--surf`/`--acc`/...), поэтому те же server-rendered страницы
google-auth автоматически получили новый вид тем же заходом, без единой
правки в самом google-auth.

## Маршрутизация через гейтвей

В [wallet-gateway](https://github.com/WalletTransactions/wallet-gateway) этот сервис — **фолбэк по умолчанию**:
всё, что не подошло под `/api/*`/`/auth/*`/`/admin/*`, идёт сюда (`/`,
`/app.js`, `/style.css`, `/favicon.svg`) — см. `WALLET_WEB_URL` в его `.env`
и `find_route()` в его `main.cpp`. Ровно та же роль, что раньше играл
wallet-bff.

**Открывать нужно адрес гейтвея**, не порт этого сервиса напрямую — иначе
`GET /auth/me`/`POST /api/wallets` из `app.js` уйдут на origin nginx (там
ничего похожего не слушает — `404`), а не на гейтвей.

## Запуск

### Через Docker/podman (`compose.yaml` в корне репозитория)

Ничего собирать не нужно — образ `nginx:1.27-alpine` + скопированные файлы,
см. `Containerfile`. Порт внутри контейнера — `80`, наружу зависит от
`compose.yaml` (сейчас `8083`).

### Без Docker (локальная разработка на Windows)

В отличие от остальных сервисов проекта, здесь не CMake-сборка — нужен
готовый `nginx.exe`:

1. Скачайте nginx для Windows: https://nginx.org/en/download.html (обычный
   `.zip`, распаковать куда угодно).
2. В распакованной папке отредактируйте `conf/nginx.conf` — либо замените
   его целиком на `nginx.conf` из этой папки (пути `mime.types` относительны
   рабочей директории nginx, сработают как есть), либо только поменяйте
   `listen 80;` на `listen 8083;` и `root html;` на абсолютный путь к
   `wallet-web/site` этого репозитория.
3. Если использовали свой `conf/nginx.conf` — скопируйте `site/*` в
   `html/` рядом; если целиком заменили конфиг — этот шаг не нужен, `root`
   уже указывает сюда.
4. Запустите `nginx.exe` (без консоли — работает в фоне; `nginx.exe -s stop`
   останавливает).

Порт `8083` — чтобы не занимать `8080`/`8081`/`8082`/`8090`, уже занятые
остальными сервисами проекта (см. их README).

## Документация (`/docs`, `/openapi.yaml`)

В отличие от трёх C++-сервисов проекта (там `GET /docs`/`/openapi.yaml`
генерирует код, см. их `src/docs.cpp`) — здесь это просто ещё два файла в
`site/`: `site/docs/index.html` (Swagger UI) и `site/openapi.yaml` (сама
спека). nginx их ничем не выделяет — обычный `try_files`, как для
`index.html`/`app.js`. Swagger UI — вендоренный статический бандл
(`site/vendor/swagger-ui/`, см. его README про версию/происхождение), не
CDN-ссылка — работает и без доступа наружу (LAN-only MVP, см.
`org/docs/TODO_mobile_sync.md`).

Спека `wallet-web` документирует ровно то, что есть — SPA-фолбэк (см. выше)
плюс эти два статических адреса; контракты `/auth/*`/`/api/*`/`/admin/*`,
которые дёргает `app.js`, — в openapi.yaml `google-auth`/`wallet-api`, не
здесь (сервис их не реализует, только вызывает через гейтвей).

## Конфигурация

Никакого `.env` у этого сервиса нет — nginx статики не читает переменные
окружения, а сама статика не содержит секретов/адресов бекендов (все
API-вызовы в `app.js` — относительные пути, резолвятся туда, куда их
направит гейтвей, см. выше). Единственное, что можно поменять — порт,
см. "Запуск" выше.
